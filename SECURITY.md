# Security

Report vulnerabilities privately to the project owner through an established private channel. No invented security contact is provided. Do not include passwords, tokens, or personal account information in an issue.

## Controls

- Better Auth 1.7.2 provides salted scrypt password hashing and verification. Minimum 12 / maximum 128 characters. Email verification required before login; public duplicate registration, reset requests, and verification requests use generic responses. A minimum response floor reduces obvious timing differences; it is not a claim of perfect network constant time.
- Signed opaque host-only HttpOnly SameSite=Lax cookies. STAGING/PRODUCTION requires Secure cookies and HTTPS. Database sessions expire after 24 hours, refresh at most hourly, and are checked without cookie caching. Logout deletes the session; reset revokes all sessions; disabling revokes sessions and every protected request checks enabled status. Database locking prevents disabled-user session insertion races.
- Better Auth owns password hashing, token validation, expiry, and reset consumption. Reset identifiers are hashed. Additional HMAC token-consumption records make verification and reset replay fail, including concurrent requests. Email links carry tokens in URL fragments, removed from browser history before form submission. No GET mutation or public mail viewer.
- Exact-origin JSON mutations at the API and web proxy, CORS allowlist, Helmet API headers, Next security headers, no raw user-controlled request IDs, strict payload allowlists, 16 KiB API body limit, parameterized SQL, transaction rollback, generic errors with no stack traces.
- PostgreSQL request throttles: 20 requests per 60 seconds per HMAC IP key and email key for auth/reset/verification. API does not trust forwarded IP headers. The local same-origin proxy therefore shares a conservative IP bucket. Before multi-user deployment, configure an authenticated trusted reverse-proxy identity/rate-limiter; never trust arbitrary X-Forwarded-For. Better Auth also has database rate limits.
- Audit events append only; mutation and TRUNCATE blocked by triggers. Privileged role/tier/enable changes are internal-only functions and require a currently enabled PLATFORM_ADMIN, transactionally audited. Runtime DB credentials must not own tables/triggers. Schema owner/superuser can defeat database controls and is trusted infrastructure.
- Application logs use an explicit allowlist of timestamp, service, level, request ID, event, safe user ID, and numeric status. No request bodies/URLs/queries/headers/raw errors. Better Auth raw log arguments are discarded. API/Next process managers and reverse proxies must also disable body/query/cookie logging.
- Validated private config; `.env`, local databases, local mail, generated native projects, and build output excluded from Git. No public env variables contain credentials. `.env.example` has invalid replacement values. Source credential-pattern scanning, npm audit at low threshold, licensing checks, and CI fail on errors.

## Threat assumptions and operational requirements

This foundation assumes an uncompromised server, dependency supply chain, database host, and secret manager. Signed session tokens are stored as sensitive authentication material by Better Auth; a database read breach may expose active session credentials. Use encrypted storage/backups, least privilege and immediate session invalidation/secret rotation on compromise. Passwords remain hashed. No auth or account data may be used for analytics or leader visibility.

Windows file modes are advisory; `.local` and `.env` inherit the current user's ACL. Use a private user account and directory ACLs; do not share or publish this workspace. Local mail contains short-lived secrets and synthetic/dev addresses: remove it when done. It is LOCAL/TEST only. Deployed mail requires authenticated SMTPS configuration; outbound production email delivery has not been exercised without owner-provided infrastructure. Delivery failures emit a sanitized `mail.failed` event and leave public responses generic to prevent enumeration during provider outages. Operators must alert on that event, restore delivery, and ask the user to resend; no durable retry queue is implemented.

No MFA, federation, public role-management endpoint, billing, health data, location, or formation permissions exist. A native signed build/device test and hosted CI require their respective environments. No commercial rollout is approved. Local bootstrap uses a project-local PostgreSQL owner for convenience; deployment must apply separate runtime grants. Daily `npm run db:maintenance` removes expired auth/rate/token records and never mutates audit events. Audit/account retention policy requires owner approval before real deployment; no arbitrary deletion policy is invented.

This workspace is inside OneDrive. Git ignore rules do not prevent synchronization by OneDrive. The generated local credentials are development-only; use a private unsynced workspace or managed secret storage before introducing real credentials or account data.
